## Context

See [proposal.md](proposal.md) for motivation — root cause and evidence come directly from a real session log where an SSID switch left `local_ip` empty and `gateway_ip` equal to the Zscaler tunnel's virtual next-hop (`100.64.0.1`) for the remainder of the session. `NetworkDiscovery.get_lan_gateway()` and `get_zscaler_info()` both use unscoped `route -n get <ip>` fallback queries against the same OS routing table; when Zscaler owns the default route, both can independently resolve to the tunnel's gateway. `classify_outage()` only sees three `ProbeResult`s (LAN/ISP/Zscaler) and has no visibility into *why* the LAN probe target was what it was — it cannot tell "real router, ICMP-suppressed" apart from "not a router at all."

## Goals / Non-Goals

**Goals:**
- Make `get_lan_gateway()`'s fallback path immune to inheriting the VPN tunnel's gateway.
- Add a last-resort sanity check (gateway == VPN virtual next-hop → treat as unknown) as defense in depth, independent of *how* the wrong value was derived.
- Give "interface has no local IP, and nothing else works either" its own visible signal instead of silently feeding a stale/substituted gateway into the existing LAN/ISP/Zscaler fault matrix.
- Distinguish a LAN gateway that has never answered ICMP this session (a permanent network characteristic) from one that was answering and has gone silent (a genuine local-network state change), so the latter — the actionable signal — isn't buried under identical-looking noise from the former.
- Reset LAN-gateway-scoped session state (the responsiveness baseline, and the overhead-statistics baseline) whenever the discovered LAN gateway address itself changes mid-session, so history from a previous network is never misattributed to a new one.
- Represent "LAN gateway has never responded, but nothing is actually wrong" with a status that doesn't read as a problem — no incident, no `DEGRADED` label — while still being visible and counted separately in the session summary.

**Non-Goals:**
- Changing `classify_outage()`'s core 3-way probe matrix or its existing fault-domain strings for genuine LAN/ISP/Zscaler faults — this change only prevents a *wrong input* from reaching that matrix, and adds one new, separate condition checked before it, plus the new status described below.
- Speeding up DHCP lease acquisition or influencing macOS network re-association — out of the script's control.
- Resetting on mere *physical* interface renaming (e.g. `en0` → `en1` with no actual gateway change) — the existing `overhead-statistics` requirement that baseline is *not* reset on physical interface change is unaffected; the new reset trigger is specifically the LAN gateway *address* changing, a different and more specific signal.

## Decisions

**Scope the fallback route query to the interface, and add a value-based sanity check.**
Two independent, additive layers of defense, matching the "belt and suspenders" pattern already used for the interface-vanish fix:
1. `get_lan_gateway()`'s fallback becomes `route -n get -ifscope <interface> 1.1.1.1` (same pattern the ISP probe already uses), so it can no longer report the tunnel's next-hop even when Zscaler owns the unscoped default route.
2. Regardless of *how* a gateway value was derived, `discover_all()` compares the candidate LAN gateway against `zscaler_info["gateway_ip"]` (the tunnel's known virtual next-hop) and discards the LAN gateway (sets it to `""`) if they match. This catches the same failure mode even if a future code path reintroduces an unscoped lookup.

Both are needed: (1) prevents the wrong value at the source; (2) is a cheap safety net that costs nothing and doesn't rely on every future lookup remembering to scope itself.

**Surface "no local IP" as a distinct DEGRADED fault string, not a new status enum — but only when connectivity is also actually down.**
Earlier draft of this decision short-circuited purely on `local_ip` being empty. Real-world testing on an iPhone Personal Hotspot (IPv6-only cellular backhaul, using 464XLAT/CLAT translation per RFC 7335) showed this is too broad: on such networks `local_ip` is *permanently* empty by design — there is no IPv4 address to assign — yet ISP and Zscaler probes succeed normally via NAT64. Labeling that healthy, working state "DHCP Pending" is actively misleading (nothing is pending; it will never resolve).

Revised condition: short-circuit to `status="DEGRADED"`, `fault="Local Interface Has No IP Address (DHCP Pending)"` only when `local_ip` is empty **and** both the ISP and Zscaler probes also fail — i.e. there is no evidence of any working path at all. If `local_ip` is empty but ISP/Zscaler succeed, fall through to `classify_outage()` as before; its existing `not lan_ok and isp_ok and zsc_ok` case (`"Local Gateway ICMP Unresponsive (ISP and Zscaler Active)"`) already describes this state reasonably (LAN target silent, everything else fine), without a name implying a transient condition that will resolve itself. This still doesn't change `classify_outage()`'s signature or its existing scenarios for genuine LAN/ISP/Zscaler faults; the log schema's `status` column keeps its existing three values for this specific decision (see the `INFO` status decision below for the one status value this change does add, for a different, narrower case).

Detecting the RFC 7335 CLAT prefix (`192.0.0.0/29`) specifically was considered as an alternative/addition, but rejected as the primary gate: it's narrow (only helps if the wrong-looking gateway happens to fall in that exact range), fragile (a magic-number special case to explain and maintain), and doesn't generalize to other reasons a machine might have working connectivity without a conventional local IPv4 address. Gating on *actual observed connectivity* (ISP/Zscaler probe results) is the general fix; a CLAT-range hint could still be added later as a purely diagnostic annotation, not a behavioral gate.

**Track per-session LAN gateway responsiveness as a baseline, and split the silent-gateway scenario accordingly.**
The `F,T,T` case in `classify_outage()` (LAN silent, ISP and Zscaler healthy) currently treats every occurrence identically. On some networks (iPhone Personal Hotspot/CLAT, or any gateway that always suppresses ICMP by policy) the LAN gateway is silent from the very first iteration and stays that way for the entire session — this is a permanent characteristic, not an event. On other networks, the gateway answers fine for a while and then genuinely goes silent — that transition is the actionable signal an operator actually cares about.

Introduce a session-scoped flag, `lan_gateway_ever_responded` (set to `True` the first time an LAN probe succeeds, never reset within a session), and split the existing scenario using it:
- **Never responded this session** → keep classifying as `DEGRADED`, but with a distinct fault string (e.g. `"Local Gateway Silent (No Response Observed This Session)"`) that doesn't imply an ICMP-suppression policy assumption the tool can't actually verify.
- **Previously responded, now silent** → `DEGRADED "Local Gateway Stopped Responding (Previously Reachable)"` — a distinctly-labeled, more actionable state, since it represents an observed change rather than a static characteristic.

This stays inside the existing `DEGRADED` bucket and only changes the fault-domain *string* plus which of two strings is chosen, based on session history rather than the single current iteration — **except** for the "never responded" branch, which is revised further below to use a new, non-`DEGRADED` status instead.

**Reset LAN-gateway-scoped session state when the gateway identity changes.**
A follow-up real-world test (Wi-Fi → iPhone Personal Hotspot mid-session) showed `lan_gateway_ever_responded` alone isn't enough: the flag is session-scoped, but a mid-session network switch means the tool is now talking to a *different* gateway that has its own, independent responsiveness history. The old Wi-Fi gateway (`192.168.178.1`) had answered, setting the flag `True`; after switching to the hotspot's CLAT gateway (`192.0.0.1`, which has never answered), the stale `True` flag produced the misleading "Stopped Responding (Previously Reachable)" label for a gateway that, on this network, had never actually responded. The overhead-statistics baseline has the identical problem for a different reason: it kept the old Wi-Fi network's latency baseline instead of establishing a fresh one for the hotspot's very different characteristics.

Both are fixed the same way, reusing the pattern already established for tunnel-interface-change detection (`tunnel-change-events` capability): track the previously-discovered LAN gateway address (`current_gw_ip`), and when a periodic re-discovery finds it has changed (both old and new values non-empty and different — the same non-empty-and-different guard the tunnel-change detection already uses, to avoid resetting on a merely transient empty reading), reset `lan_gateway_ever_responded = False` and reset the `OverheadStats` instance exactly as the tunnel-change and daily-rotation code paths already do (`overhead = OverheadStats(window_size=args.overhead_window)`, `silent_healthy_count = 0`, `last_heartbeat_time = time.time()`). This does not touch or contradict the existing `overhead-statistics` requirement that baseline is not reset on a mere *physical* interface rename — that scenario is about the interface name changing without the gateway changing; this new trigger is specifically about the gateway *address* changing, a stronger and more specific signal that the network itself is different.

**Introduce a new `INFO` status for "LAN gateway never responded, nothing is actually wrong."**
The user explicitly requested this, and on reflection the earlier rejection of a fourth status doesn't hold for this specific case: a LAN gateway that has *never* answered this session, while ISP and Zscaler are both healthy, is not a degradation — it's an expected, often-permanent characteristic of the current network (CLAT/iPhone Personal Hotspot, or any router that simply never answers ICMP). Continuing to label it `DEGRADED` misrepresents session health stats and opens an incident for something that was never actually a problem.

Introduce `INFO` as a fourth status value, used only for this one case (the "never responded, ISP/Zscaler both healthy" branch of the `F,T,T` split above). The "previously responded, now silent" branch is unaffected and remains `DEGRADED` — it's a real transition, which is exactly the actionable signal this whole effort is trying to preserve. Concretely:
- `classify_outage()`'s never-responded branch returns `("INFO", "Local Gateway Silent (No Response Observed This Session)")` instead of `DEGRADED`.
- The main loop's incident-opening condition (`if status != "HEALTHY":`) is widened to `if status not in ("HEALTHY", "INFO"):` so `INFO` behaves like `HEALTHY` for incident lifecycle and silent-mode heartbeat/streak purposes — it does not open an incident and does not interrupt a healthy streak.
- `status_counts` gets a fourth key, `"INFO"`, and the session-summary percentage breakdown iterates over all four so a user can see, e.g., "20% of this session the LAN gateway was expectedly silent" as a distinct line from genuine `DEGRADED` time.
- The console gets a fourth color branch (a distinct, non-alarming color) for `[INFO]`.
- No log-schema version bump: `__log_schema__` covers column format (added/removed/reordered columns), not the set of values a column may contain — `status` was already a free-form string, not a validated enum, in the logfile format itself.

The exact word `INFO` is a naming choice, not load-bearing; it was chosen for brevity and because it reads clearly in the existing `[HEALTHY]`/`[DEGRADED]`/`[OUTAGE]` bracket convention. It can be renamed later without further design impact.

## Risks / Trade-offs

- [Risk] The ifscope'd fallback may itself fail to return anything on some macOS network configurations (e.g. if the interface truly isn't routable yet) → Mitigation: existing empty-string return / "Searching..." banner behavior is unchanged; this only prevents a *wrong* value, it doesn't guarantee a value.
- [Risk] Comparing gateway to the Zscaler virtual next-hop assumes `zscaler_info["gateway_ip"]` is itself reliably the tunnel's true next-hop — if that's ever wrong, the sanity check could discard a legitimate LAN gateway that happens to coincide with it → Mitigation: this is a narrow equality check only applied when Zscaler is reported active, and the earlier log evidence shows genuine LAN gateways and the reported Zscaler vgw can coincide during normal operation (before Zscaler asserts the default route) — worth flagging as an explicit follow-up test case, not silently assuming.
- [Risk] "No local IP" DEGRADED state could mask a genuine simultaneous LAN/ISP/Zscaler fault that happens to coincide with a DHCP renewal window → Mitigation: re-evaluate normally the moment an IP reappears; don't suppress incident tracking, only relabel the fault string.
- [Risk] Requiring ISP *and* Zscaler to also fail before using the "no local IP" label means a genuinely IP-less-and-broken interface where, say, only Zscaler happens to still respond (stale/cached state) won't get this label, and instead falls through to whatever `classify_outage()` produces for that partial-success combination → Mitigation: acceptable trade-off — those partial-success combinations already have reasonably descriptive existing fault strings (e.g. "ISP Issue", "Zscaler Issue"), and this change's goal is specifically to stop mislabeling healthy IPv6-only/CLAT connectivity as broken, not to relabel every combination involving an empty `local_ip`.
- [Risk] The `lan_gateway_ever_responded` baseline resets every session (matching the existing overhead-baseline pattern), so a fresh session on a network whose gateway happens to be briefly slow to answer at startup could misclassify a few early transient failures as "never responded" rather than "stopped responding" → Mitigation: acceptable — this only affects fault-string wording during the first few iterations, not severity (both cases are DEGRADED), and the label self-corrects the moment the gateway answers once.
- [Risk] Detecting a LAN gateway identity change relies on periodic re-discovery (`should_rediscover()`'s cadence), so the reset may lag a few iterations behind the actual network switch, during which the old baseline is briefly used against the new network → Mitigation: acceptable and bounded — the same lag already exists for tunnel-change detection, and worst case is a few iterations of a slightly-off baseline/label before the reset catches up, not a persistent misclassification.
- [Risk] Introducing a fourth status value touches several call sites (`status_counts` initialization, the session-summary loop, the console color mapping, the incident-opening condition, `--silent` heartbeat/streak tracking) — more surface area than the earlier, narrower decision assumed → Mitigation: every touched site already treats `status` as an open string key/comparison (no hardcoded enum validation), so each site needs a small, additive change rather than a structural rewrite; full test suite coverage is added for the new status alongside the change.

## Migration Plan

Single-file behavioral fix, no data migration. Run the full test suite, and if practical, re-run the same manual SSID-switch scenario that surfaced the bug to confirm the log no longer shows a substituted Zscaler gateway as the LAN gateway.
